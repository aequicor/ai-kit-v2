# `.aikit/manifest.json`

Манифест пользовательского проекта — источник истины для CLI AI-Kit. Лежит в `.aikit/manifest.json` в корне проекта.

## Назначение

Манифест описывает, какие бандлы и с какими значениями `inputs` применяются к каким частям пользовательского проекта и под каких агентов. CLI читает этот файл при `apply` / `validate` / `update` и по нему воспроизводит состояние сгенерированных файлов.

## Расположение

```
<project root>/
├── .aikit/
│   ├── manifest.json         # этот файл
│   └── bundles/              # опционально: внешние бандлы (.zip или папки)
│       └── opencodekit-2.1.3.zip
└── ...
```

## Полная схема

```json
{
  "aikitVersion": "1.0.0",
  "applications": [
    {
      "id": "backend",
      "path": "./backend",
      "targets": {
        "claude": {
          "bundle": "simple-kit@0.0.1",
          "source": "remote",
          "inputs": {
            "projectName": "billing-service",
            "language": "kotlin",
            "useCoroutines": true
          }
        },
        "opencode": {
          "bundle": "opencodekit@2.1.3",
          "source": "./.aikit/bundles/opencodekit-2.1.3.zip",
          "inputs": {
            "projectName": "billing-service",
            "language": "kotlin",
            "useCoroutines": true
          }
        }
      }
    },
    {
      "id": "root",
      "path": ".",
      "targets": {
        "claude": {
          "bundle": "simple-kit@0.0.1",
          "source": "./.aikit/bundles/simple-kit/0.0.1",
          "inputs": { "projectName": "billing-service" }
        }
      }
    }
  ]
}
```

## Поля верхнего уровня

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `aikitVersion` | string (SemVer) | да | Версия CLI AI-Kit, которая записала манифест. Используется для диагностики совместимости. Совместимость формата определяется SemVer самого CLI: MAJOR-бамп AI-Kit = возможное breaking-изменение манифеста. |
| `applications` | array | да | Список применений бандлов. Может быть пустым (валидно, но `apply` ничего не сделает). |

## Объект `application`

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `id` | string | да | Уникальный в пределах манифеста идентификатор. Используется в логах и в флагах CLI (`--only <id>`, `--skip <id>`). |
| `path` | string | да | Путь к подпроекту относительно корня проекта. Допустимы `"."`, `"./backend"`, `"./apps/web"`. Запрещены абсолютные пути и выход за пределы проекта (`../`). |
| `targets` | object | да | Карта `<agent> → target`. Ключ — семантическое имя агента (`claude`, `opencode`, `cursor`, ...). |

## Объект `target`

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| `bundle` | string | да | Идентификатор бандла в формате `name@version`. Версия должна совпадать с версией, объявленной в манифесте самого бандла, иначе `apply` падает с ошибкой. |
| `source` | string | да | Откуда брать бандл: `"remote"` для точной официальной версии `bundles/<name>/<version>/`, `remote:<owner>/<repo>/<path>[@<branch>]` для произвольного GitHub-репозитория либо путь к локальной директории/ZIP. |
| `inputs` | object | да | Плоский объект со значениями входов бандла. Валидируется против `inputs.schema` внутри бандла (типы, required, enum). Значения по умолчанию из схемы бандла **не** дублируются в манифест — это позволяет апгрейду бандла безопасно подменять дефолты. |

## Ссылочные значения в `inputs`

Значения в `inputs` могут содержать встроенные ссылки на внешние источники. Ссылки вставляются прямо в строку — синтаксис аналогичен строковым шаблонам Kotlin:

```json
"inputs": {
  "projectName": "${env:PROJECT_NAME}",
  "apiUrl":      "${env:API_HOST}-${env:ENV}.internal",
  "dbPassword":  "${file:secrets/db.txt}",
  "awsKey":      "${envFile:config/prod.env:AWS_ACCESS_KEY}"
}
```

### Поддерживаемые виды ссылок

| Синтаксис | Разрешается в |
|---|---|
| `${env:VAR_NAME}` | Значение переменной среды `VAR_NAME` |
| `${file:relative/path}` | Содержимое файла (обрезается пробел/перенос в конце) |
| `${envFile:relative/path/file.env:KEY}` | Значение ключа `KEY` из `.env`-файла |

Ссылки можно смешивать с литеральным текстом: `"my-${env:APP}-svc"`.

### Правила

- **Пути** в `${file:...}` и `${envFile:...}` должны быть относительными: запрещены `..`, абсолютные пути (`/`, `C:\`).
- **Парсинг `.env`**: строки `KEY=VALUE`, комментарии (`# ...`) пропускаются, значения в одинарных или двойных кавычках — кавычки убираются.
- **Ошибка**: отсутствующая переменная среды, несуществующий файл или отсутствующий ключ — `apply` падает с сообщением вида `input 'projectName': env var 'PROJECT_NAME' is not set`.
- **Для не-строковых полей** (bool, int, double): всё значение должно быть одной ссылкой — после раскрытия строка конвертируется в нужный тип.
- **Неизвестные** `${...}` (не `env:`, `file:`, `envFile:`) проходят без изменений.

## Правила резолвинга и поведения

### Резолвинг бандла

1. Если `source == "remote"` — CLI разрешает `name@version` в `bundles/<name>/<version>/` официального репозитория.
2. `internal` и `embedded:` отклоняются с инструкцией перейти на `remote` либо скачать бандл отдельно и указать локальный путь.
2. Если `source == "remote"` — эквивалент явной ссылки `remote:aequicor/ai-kit-v2/<name>@main`, где `<name>` — имя из `bundle` без версии.
3. Если `source` начинается с `remote:` — бандл скачивается из GitHub-репозитория (см. «Удалённые бандлы» ниже).
4. Если `source` — путь, CLI читает бандл оттуда. Версия в манифесте бандла должна совпадать с версией в `bundle`. Несовпадение → ошибка `bundle version mismatch: expected <X>, found <Y>`.
5. Путь не существует → ошибка `bundle source not found: <path>`.

### Удалённые бандлы (`remote`)

Форма ссылки: `remote:<owner>/<repo>/<path/внутри/repo>[@<branch>]`. Ветка по умолчанию — `main`. Все компоненты валидируются по строгим allow-list'ам символов (буквы, цифры, `._-`; сегменты `..` и `.` запрещены) — ссылка не может протащить метасимволы shell в команды скачивания.

Поведение:

- **Скачивание.** При первом чтении CLI выполняет `git ls-remote` (получает commit sha вершины ветки) и, если этой ревизии нет в кэше, `git clone --depth 1`. Требуется `git` в `PATH` и доступ к сети; при их отсутствии — понятная ошибка.
- **Кэш.** Скачанное складывается в `.aikit/cache/bundles/<owner>__<repo>__<sha>/`. Повторный `generate` при неизменившейся вершине ветки сеть для скачивания не использует (только быстрый `ls-remote`). Папку `.aikit/cache/` следует добавить в `.gitignore`.
- **Версионирование.** Remote-бандл отслеживает **ветку**: каждый `generate`/`update` берёт её текущую вершину. Фактический commit sha записывается в `manifest.lock.json` (`resolvedSha`) — установка воспроизводима постфактум и аудируема. Поле `bundle` (`name@version`) сверяется с `bundle.json` скачанной ревизии, как и для остальных источников.

### Куда генерируется результат

Целевая папка внутри `application.path` определяется **самим бандлом**, а не манифестом. Например, бандл `simple` для агента `claude` знает, что кладёт файлы в `<application.path>/.claude/`. Манифест эту деталь не фиксирует.

### Конфликты файлов

CLI на этапе `apply`:

1. Строит виртуальную файловую систему всех генераций по всем `applications` и `targets`.
2. Если два разных target пишут в один и тот же путь — падает с ошибкой `conflict at <path>: targets [<app>.<agent>, <app>.<agent>]`.
3. Если генерируемый файл уже существует в проекте и не принадлежит предыдущему `apply` (нет в lock-файле) — падает с `conflict with user file: <path>`. Защита от затирания пользовательских правок.
4. Запись на диск происходит только после успешной проверки всей виртуальной FS. Частичных применений нет.

### `id` и идемпотентность

`id` стабилен между запусками — по нему CLI сопоставляет предыдущее состояние (через lock-файл) с новым и понимает, какие файлы удалить при удалении target из манифеста.

## Что не входит в манифест

- **Lock-файл** (`.aikit/manifest.lock.json`) — отдельный артефакт с хешами сгенерированных файлов. Создаётся CLI автоматически при `generate`/`update`, в git коммитится. Используется командами `update` (для diff'а и удаления orphan-файлов) и `remove` (как реестр того, что можно безопасно удалить). Формат — см. [`MANIFEST_LOCK_JSON.md`](MANIFEST_LOCK_JSON.md).
- **Схема `inputs`** — лежит внутри бандла, не в манифесте проекта.
- **Целевые пути генерации внутри `application.path`** — знает бандл.

## Несколько манифестов: переключение через local.properties

Один проект может содержать несколько манифестов для разных режимов работы агента (интерактивный, автономный, CI и т. д.). Активный манифест задаётся через `.aikit/local.properties` (per-developer, не коммитится) или через переменную окружения:

```
.aikit/
├── manifest.interactive.json
├── manifest.autonomous.json
└── local.properties       ← не коммитить: содержит "manifest=..."
```

```properties
# .aikit/local.properties
manifest=.aikit/manifest.autonomous.json
```

При смене манифеста `kit-setup generate` автоматически удаляет файлы предыдущей установки (после успешной валидации нового манифеста в памяти) и применяет новую конфигурацию. Битый манифест не уничтожит рабочее состояние.

Подробнее — в [`MODES.md`](MODES.md).

